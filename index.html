1. Response time

Speech to text19.9 s0.6 s
Retrieval and LLM10.4 s5.0 s

Total32.2 s6.5 s

RTX 4070 SUPER (12 GB), Windows 11, DeepSeek-R1 8B in both cases. Before: 2 runs (29.3 and 35.0 s). After: 6 warm runs (5.3 to 8.0 s).

Whisper was reloaded on every request

The speech-to-text step loaded the Whisper turbo model from disk each time. Loading took 5.8 s. I load the model once at startup. This cost does not depend on having a 12 GB card, although the load time will differ on other machines.

The gemma3 correction pass competed for GPU memory

Each transcript was sent to gemma3 for spelling correction. In Ollama, gemma3 took 2.9 GB and DeepSeek-R1 up to 6.0 GB. Those two should fit in 12 GB, but not together with Whisper. When gemma3 needed loading, the correction took 8.0 s; when it was already resident, 0.5 s. With Whisper and gemma3 both resident, DeepSeek ran 16% on the CPU and the retrieval and LLM step took 29 to 38 s.

The pass is now off by default. Whisper receives a short list of domain terms (afterloader, Iridium-192, dwell position and others) as its decoding prompt. I have not compared transcription accuracy between the two approaches. A 32 GB RTX 5090 should have room for all three models.

Two smaller changes

  • DeepSeek stays loaded between questions (keep_alive=-1).
  • The prompt asks for at most four short spoken sentences, since the answer is read aloud.

Optional: qwen3:8b

On 14 questions, the retrieval and LLM step averaged 0.9 s with qwen3:8b (thinking off) and 4.5 s with DeepSeek-R1. In a side-by-side check the answers were broadly similar. This is a small sample without formal scoring. My copy now defaults to qwen3:8b; DeepSeek remains available through a setting.

2. BM25 retrieval

The index held 5 fixed chunks

The knowledge base has 249 chunks. BM25 could see only the 5 closest to a placeholder string, and with k = 5 it returned all of them for every question. They were then merged with the vector results, so the LLM received 9.9 chunks on average instead of 5.0.

The default tokenizer was too simple

LangChain's default splits on whitespace only. Matching was case-sensitive (Remote did not match remote), punctuation stayed attached (Iridium-192, did not match Iridium-192), and stop words were scored.

Fix

words = re.findall(r"[a-z0-9]+(?:[-.][a-z0-9]+)*", text.lower())
return [w for w in words if w not in _STOPWORDS]

_bm25 = BM25Retriever.from_documents(
    list(_vectorstore.docstore._dict.values()),
    preprocess_func=bm25_tokenize,
)

The index is built once and cached. The 0.5/0.5 fusion weights and k = 5 are unchanged.

A question is a hit when the retrieved text contains at least 60% of the keywords in the reference answer. Keyword coverage is the average share. This is a quick check of retrieval, not a RAGAS score and not a measure of answer correctness.

3. PDF text extraction

The StatPearls PDF was printed from a browser (its producer field reads Skia/PDF). pypdf's default plain mode put almost every word on its own line. The same page in both modes:

plain:  '\n \neliminate\n \nand\n \nshrink\n \ntumors\n.\n \nBrachy-\n \nmeans\n ...'
layout: 'tumors. Brachy- means short distance in Greek. It was first used in ...'

Whitespace made up 29.7% of the StatPearls chunks, compared with 15.1% after the rebuild. The text was also split page by page at 512 characters, and page headers and the reference list were indexed as content.

Fix

  • Extract with pypdf's layout mode.
  • Remove page headers and footers, citation markers and the StatPearls reference list.
  • Split each document as one text, in 800-character chunks with 150 overlap.

At the original chunk size, cleaning adds one hit. The rest of the gain comes with longer chunks, which give the model more text and make a hit easier. I also chose the chunk size on these same 52 questions, so 34 is likely optimistic.

One example: asked which system emphasizes higher dose at the periphery, the model used to answer Quimby. It now answers Manchester, but adds that the central dose is hotter, which the source says about Quimby.

4. Risk factor

gpt-4o-mini will be shut down

OpenAI's deprecations page lists gpt-4o-mini-2024-07-18 with a shutdown date of January 14, 2027 (notice given October 14, 2026). It is one of the two LLMs evaluated in the paper. After that date the gpt-4o-mini results cannot be rerun.

5. Not done yet

  • The full RAGAS evaluation has not been run on the new setup.
  • Nothing has been tested on the Quest 3 headset.
  • The timings come from one PC and few runs.
  • One evaluation question, on the four primary QA endpoints, has no supporting passage that I could find in the two indexed documents, so a refusal there looks correct.
